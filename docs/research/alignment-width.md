# Alignment and width: source checks (#285)

The source checks behind tier 1 job `alignment-width` (rank 36) of the coverage ledger. Read 19 Oct 2026, by curl and text extraction; dates are each page's own.

## 1. Sources checked

| Rows | Record | Source opened, and what it says |
|---|---|---|
| LAY-46, LAY-47, LAY-48, TYS-56, TYS-60 | `vault.line-length` | Baymard, "Readability: The Optimal Line Length" (10 May 2022): "The optimal line length for body text is 50–75 characters"; fatigue at "100+ characters". W3C Understanding SC 1.4.8 (updated 6 Sep 2026): "no more than 80 characters or glyphs (40 if CJK)", as a mechanism: "Content is not required to use these values". webtypography.net 2.1.2 (Bringhurst): 45–75 "for a single-column page set in a serifed text face in a text size"; "For multiple column work, a better average is 40 to 50 characters". Typography Handbook (updated for 2026): "40–50 CPL per column"; "UI text, captions, and footnotes often work better at 35–50 CPL"; "let the measure reduce naturally with the viewport rather than enforcing a minimum". USWDS Typography and measure tokens (measure page updated 15 May 2024): "Large text can have a shorter measure"; measure 1 "for larger text (like a subheading or intro text)"; "Short passages can have measure outside the ideal range"; measure 6 for "captions of fewer than three lines". Butterick, "Line length" and "Responsive web design" (undated): "45–90 characters, including spaces"; "Regardless of screen width, the optimal line length is still 45-90 characters". Checks `rule-interactions.md:199`, `principle-interactions.md:154` and `notes-coverage.md:30` against Bringhurst, Butterick, Baymard and WCAG as quoted. |
| TYS-59, TYS-60 | `vault.measure-unit` | Butterick, "Responsive web design": `ch` "simply denotes the width of the zero"; "not a useful proxy". USWDS measure tokens: in `ex`, measure 1 = 44ex to measure 6 = 88ex; 66 characters (measure 2) "a good target for long texts". Baymard: "around 70ch or 34em (note that this value will need to be adjusted slightly up or down depending on the font used)". Every Layout, "Axioms": "Enforcing a specific measure would mean setting a fixed width. Many users would experience horizontal scrolling and broken zoom functionality". Checks `manta-design-migration.md:70` (T4), whose own measurement (68ch set about 85 characters) the `ch`-is-a-zero quotes explain. |
| TXL-44 | `vault.text-align` | GOV.UK Font override classes (Frontend v6): "Do not 'justify' blocks of body copy text". USWDS Typography: justified text "does not yet display well enough in a web browser to be considered a best practice". Understanding 1.4.8: F88, justified text a failure; "rivers of white". Butterick, "Justified text": "you must also turn on hyphenation"; on a web page "I'll always left-align". webtypography.net 2.1.3: "Many unserifed faces look best when set ragged". Checks `adopt-or-build.md:45` against Butterick and WCAG 1.4.8. |
| TXL-49 | `vault.justify-space` | Butterick, "Justified text": "Please—put it between the words". MDN `text-justify` (modified 26 Jul 2026): `inter-word` for "languages that separate words using spaces", `inter-character` for "languages like Japanese"; "Limited availability", not Baseline. |
| TXL-45 | `vault.centred-text` | Butterick, "Centered text": "acceptable when used for short phrases or titles"; "Whole text blocks should not be centered". Latin, "5 keys to accessible web typography" (16 Jun 2019): "Don't center-align paragraphs that are longer than 2 or 3 lines of text", the only number found. Dannaway, UI design tips, tip 15 (updated 3 Jul 2026): "Centre alignment can work for headings and short text". Understanding 1.4.8 says nothing on centring. Checks `notes-coverage.md:59` against Butterick and WCAG 1.4.8. |
| TXL-46 | `vault.alignment-count` | Dannaway, UI design tips 14, tip 8 (updated 3 Jul 2026): "Sticking with a single alignment (or as few as possible) helps to simplify an interface". impeccable 4.5.0 distill.md:62: "Pick left or center, stick with it". NN/g, "Why Does a Design Look Good?" (2021, modified 13 Nov 2025): "Any alignment inconsistencies should be purposeful". |
| LAY-50, LAY-51 | `vault.text-columns` | Butterick, "Columns" ("Fine in print, not on the web"): "a web page has an indefinite bottom edge"; columns help with "a small amount of text or a list of links that can fit on a browser single screen". MDN Multiple-column layout (modified 12 Oct 2026): `column-span: all`, a spanning subhead as its example; no rule on when to use columns. |
| TXL-60 | `vault.side-indent` | Butterick, "Line length": "establish the basic length using page margins"; side indents for "special situations (for instance, block quotations)"; "start with long enough lines so that the indented parts also fall within the target range". |
| LAY-43, LAY-45, LAY-49 | `vault.content-width` | Atlassian Grid: Fixed-wide 1296px "default", for "Dashboards, directories, search results"; Fixed-narrow 864px for "long-form content"; fluid, "No maximum", for boards, "Use sparingly". GOV.UK Layout: "The default maximum page width is 1020px"; main content "in a two-thirds column"; govuk-frontend sets `$govuk-page-width: 960px`. USWDS layout grid (updated 6 Nov 2024): `grid-container` at 1024px. USWDS identifier (updated 7 Nov 2024): "Use the same max-width as your site footer", the only source on footer bands. Atlassian Empty state: "464px", narrow "304px", the only source on empty-state width. |
| LAY-44 | `vault.capped-centre` | Atlassian Grid: "sit centered in the main content area". USWDS: "grid-container centers the container". govuk-frontend `_width-container.scss`: "just centre the content", auto side margins. MDN Box alignment in block layout (modified 20 Nov 2025): auto margins "push a block into the center". Apple HIG Layout (updated 9 Sep 2026): "keep content horizontally centered at very large sizes". No source read puts the container left. |
| LAY-24 | `vault.alignment-lines`, `vault.alignment-break` | Atlassian Grid: "Only top-level containers need to align to the grid"; buttons and icons "do not need to"; "Don't allow content to overflow into gutters or margins"; headers "may break out". NN/g "Using Grids in Interface Designs" (2022, modified 11 Jun 2025): break the grid "as long as you have a valid reason". NN/g "Why Does a Design Look Good?": "keep alignment consistent across your different pages and elements". Checks `notes-coverage.md:231` against its own source, Wagemans et al. 2012 (Psychological Bulletin 138(6):1172–217, abstract read on PubMed): good continuation and parallelism among "classical" grouping principles. Checks `notes-coverage.md:71` (a text column's place in a wide section): no source decides left or centred; GOV.UK sets text left in two thirds, Atlassian centres a block of 8–12 columns, so the record asks only that the choice repeat. Counter-evidence: Zelchenko et al., arXiv 2308.12201 (Aug 2023, preprint): aligned icon arrays hurt location recall; about object arrays, not text edges. |
| LAY-88 | `vault.optical-alignment` | Refactoring UI, "Redesigning Laravel.io" (4 Oct 2017, read from web.archive.org): a button aligned to a padded list's box "feels a bit 'off'"; moved down, it "definitely looks better". Krehel, "Optical Alignment" (undated; live page gone, archive capture Oct 2025): "it is best to align items optically instead". Butterick, "Grids": "the eye must always be the final judge". No design system read (Atlassian, GOV.UK, USWDS, Apple, NN/g) states an optical-alignment rule. |
| TXL-50, TXL-51, TXL-52 | `vault.table-align` | Rutter, Web Typography, "Numerals and tables" (PDF, pp. 127–144): "aligned left"; "Right-align numbers"; "consistent precision"; "align numbers to the decimal point"; "match the alignment of headings to the alignment of the data"; "tabular lining numerals". GOV.UK Table (updated Feb 2024): "align the numbers to the right"; numeric header and cell classes alike. USWDS Table (updated 18 Aug 2026): "Right-align numerical data"; none for "phone numbers, zip codes, dates". MDN Styling tables (modified 18 Aug 2026): "align text to the left and numbers to the right". Butterick, "Grids of numbers": "Zip codes are aligned left"; centres one heading over numbers, against Rutter. Checks `text-presentation.md:165` against its own source, Butterick, "Alternate figures": "tabular figures are essential for one purpose: vertically aligned columns, like you find in grids of numbers". |
| TYS-58 | `vault.table-width` | Rutter: a table "may need to be wider than the 45 – 75 characters". impeccable 4.5.0 operate.md:16: "tables at 120ch+ are fine". USWDS Table: "apply a horizontal scrollbar if the columns exceed the available width"; directory lists stacked. |

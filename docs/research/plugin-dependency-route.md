# design-vault#244 (map #243): how the plugin ships and runs a third-party checker — 15 Oct 2026

**Question.** How can a Claude Code plugin ship and run a third-party checker from its install folder? The install folder has no `node_modules`. That is the reason #163 did not use axe-core. For each route, this note gives the cost in install time, the offline behaviour, the version pinning, the supply-chain exposure, and the fit with the AGENTS.md dependency rule. The routes are: (a) a vendored single-file build that Playwright injects; (b) `npx` or `uvx` at run time; (c) a pinned install step on first use; (d) a bundle; (e) the dependency mechanism of Claude Code plugins.



## 1. How the vault's dependencies reach a user's machine today

1. The plugin declares no dependency. `plugin/.claude-plugin/plugin.json` has only `name`, `description` and `author`. The `plugin/` folder has no `package.json`, `requirements.txt`, `pyproject.toml` or lockfile (`find plugin -name package.json -o -name 'requirements*.txt' -o -name pyproject.toml` finds nothing).
2. The Node scripts in the plugin use only Node built-ins (`crypto`, `fs`, `os`, `path`, `util`, and `node:` imports). No plugin `.js` file calls `require()` on an npm package (grep of `plugin/skills/*/scripts/*.js` and `plugin/review-page/*.js`).
3. The Python scripts import the machine-wide Python. On this machine that is miniforge: `/home/lucmo/miniforge3/bin/python3`, with playwright 1.61.0, numpy 2.4.6, Pillow 12.3.0, scipy 1.16.3 in `miniforge3/lib/python3.12/site-packages`.
4. Nothing installs these packages for the user. The scripts only tell the user what to do when an import fails:
   - `check-flow.py:185-190` `INSTALL_HINT`: "On this machine Playwright is the Python package under miniforge, installed once per machine rather than per repo: `python3 -m pip install playwright` / `python3 -m playwright install chromium`". `run_browser()` (`check-flow.py:1048-1063`) catches `ImportError` and a missing browser, prints the hint, and exits 3. All browser scripts use `chromium()` and `run_browser()` from this file.
   - `cutout.py:127-129`: "`python3 -m pip install numpy pillow scipy`". `client-originals.py:85-86`: "`python3 -m pip install Pillow`".
5. The dependency versions are not pinned anywhere. `pip install playwright` takes the latest release. The Chromium build follows the Playwright release that pip selected.
6. `test/all.sh` (the `registry` list, lines 14-28) tags each Python suite `images` (numpy, Pillow, scipy) or `chromium` (Playwright and its Chromium). Before a run it checks each tag that a selected suite needs, and prints `MISSING ... — install: python3 -m pip install ...`. It does not install. It is a repo test gate, not a user install step.
7. README §Installing the plugin on a second machine (README.md:168-170) lists only `gh auth login`, `claude plugin marketplace add lucmoseley/claude-plugins` and `claude plugin install design-vault@lucmoseley`. It does not name Python, Playwright, Chromium, numpy, Pillow or scipy. Thus on a second machine the first script run fails with exit 3 and the install hint. The README says that section is "Documented, not yet run".
8. The repo root has a `package.json` with one devDependency, `@wasm-fmt/shfmt` 0.2.7, and a `package-lock.json` and `node_modules/@wasm-fmt`. It came with workflow-core v1.3.14 (commit 9e252be, #181). It serves the repo's format gate only. The marketplace installs only `plugin/`, so this `node_modules` never reaches a user. The axe-core reason in #163 ("the repo had no `package.json`") is thus half out of date, but the install-folder half is still true.
9. **Conclusion for §1.** The current route is "the user installs it machine-wide, by hand, unpinned; the script prints the command when it is missing". Any new route is better than this one on pinning. A new route that needs a second manual step adds to a step that is already manual and undocumented in the README install section.

## 2. How workflow-core handles its own Node dependencies

1. workflow-core 1.3.14 ships a `package.json` that is a plugin manifest (name, version, skills, commands, agents). It has no `dependencies` and the install folder has no `node_modules` (`ls` of `/home/lucmo/.claude/plugins/cache/workflow-core/workflow-core/1.3.14/`).
2. Its scripts that need an npm package read that package **from the adopting repo's own `node_modules`**, not from the plugin:
   - `scripts/lib/formatters.js:66-80` `loadShfmt()`: `createRequire(<cwd>/package.json)("@wasm-fmt/shfmt")`, then a fallback from the plugin's own file. When both fail, `check-shfmt.js` reports BROKEN: "@wasm-fmt/shfmt is not installed — run npm install."
   - `scripts/check-skill-frontmatter.js:13-16`: "SHIPS, AND READS js-yaml FROM THE ADOPTER'S OWN INSTALL through lib/host-package.js (workflow-core#1380). Where it is absent the run is BROKEN, naming the install, and the commit is refused".
3. The adopter installs the package with a pinned, script-free command that the migration note gives: `npm install --ignore-scripts --save-dev --save-exact @wasm-fmt/shfmt@0.2.7` (`migrations/v1.3.14.md:528`, `:541`), and commits `package.json` and `package-lock.json`.
4. **Fit for the vault.** This pattern works for workflow-core because its scripts run on the adopter's own repo at commit time, and each adopter is a dev repo with npm. It does not fit the design-vault plugin well: a design round runs in a consumer project (for example a client site repo). That repo may not have a `package.json`, and an axe-core devDependency in each client repo is a per-project install, not a per-machine one. It would also put an unrelated devDependency into every client repo.

## 3. What Claude Code itself gives a plugin (official docs, read 15 Oct 2026; Claude Code here is 2.1.300)

Sources: plugin manifest reference `code.claude.com/docs/en/plugins-reference` (redirects to the manifest reference); `plugins/loading.md`, `plugins/components.md`, `plugins/troubleshooting.md`, `plugins/dependencies.md` under `code.claude.com/docs/en/`; `anthropics/claude-code` `CHANGELOG.md` on `main`.

1. **The plugin's install folder is a copy, and it changes with each version.** "Every other marketplace plugin: Claude Code copies the plugin into `cache/<marketplace>/<plugin>/<version>/` at install and loads that copy. Files outside the plugin directory aren't copied" (loading.md:191). "`${CLAUDE_PLUGIN_ROOT}` changes when the plugin updates, so don't write state there" (manifest reference §Environment variables). A previous version directory is removed 14 days after an update (loading.md:205). The vault's marketplace entry is a `git-subdir` source with `path: "plugin"` (`~/.claude/plugins/marketplaces/lucmoseley/.claude-plugin/marketplace.json`). Thus the plugin root is `plugin/`, not the repo root. The repo-root `package.json` is not in the copy.
2. **Claude Code installs a plugin's npm dependencies automatically.** "When Claude Code copies a plugin into the cache, it also installs the plugin's Node.js package dependencies there, so the plugin's hooks and MCP servers can load them" (loading.md:211). It runs at install, at update, and "at session start when an enabled plugin isn't cached yet, such as on a new machine" (loading.md:218-221). Conditions and limits (loading.md:225-262):
   - The plugin root must contain both `package.json` and a supported lockfile: `bun.lock`, `npm-shrinkwrap.json` or `package-lock.json` (lockfileVersion 2 or 3). `yarn.lock`, `pnpm-lock.yaml` and `bun.lockb` get no install.
   - "every dependency must be a registry package pinned in the lockfile to an exact version"; download links must be `https`.
   - "Frozen resolution: the install uses exactly the versions the lockfile pins".
   - "No lifecycle scripts: `--ignore-scripts`".
   - The package manager runs in a separate folder, so the plugin's `.npmrc` and `.env` are not read.
   - "60-second timeout".
   - "You can't turn the automatic install off."
   - It runs the package manager from the user's `PATH`. With no `npm` on the machine, the install is skipped and `/plugin` shows "were not installed, because ..." (troubleshooting.md:764).
   - When it fails, "the plugin still loads, but the parts of it that need the missing packages may not work" (loading.md:266). `claude plugin update` retries an install that did not finish (since 2.1.287).
   - Changelog dates: auto install fixed for marketplace plugins in 2.1.105 ("Fixed marketplace plugins with `package.json` and lockfile not having dependencies installed automatically after install/update"); registry-only from 2.1.286; retry and listing note from 2.1.287.
   - The docs say "runtime dependencies" (loading.md:268). They do not say in words whether `devDependencies` are installed. **Not verified**: put the checker under `dependencies`, not `devDependencies`.
3. **`${CLAUDE_PLUGIN_DATA}` exists.** It "resolves to `~/.claude/plugins/data/<id>/`, created on first reference and kept across plugin updates", for "Installed dependencies such as `node_modules`, generated code, and caches" (manifest reference). `<id>` for the vault is `design-vault-lucmoseley`. That directory exists on this machine and is empty (`ls ~/.claude/plugins/data/design-vault-lucmoseley`). It is deleted when the plugin is uninstalled from its last scope, unless `--keep-data`. Added in 2.1.78 (changelog).
4. **A SessionStart hook can run an install.** The components page gives this example, for when the automatic install is not enough (components.md §Install dependencies into the data directory):
   `diff -q "${CLAUDE_PLUGIN_ROOT}/package.json" "${CLAUDE_PLUGIN_DATA}/package.json" >/dev/null 2>&1 || (cd "${CLAUDE_PLUGIN_DATA}" && cp "${CLAUDE_PLUGIN_ROOT}/package.json" . && npm install) || rm -f "${CLAUDE_PLUGIN_DATA}/package.json"`.
   loading.md:270 names this route for "packages that need their lifecycle scripts to build, Python dependencies, plugins locked with Yarn or pnpm, and dependencies that aren't registry packages". Hook processes receive `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR` in their environment.
5. **The Bash tool does not get these variables.** "The variables aren't present in the environment of commands Claude runs through the Bash tool, in the main session or in a subagent. In skill, command, and agent content, write the `${...}` reference in the Markdown body instead, and Claude Code substitutes the path inline" (manifest reference §Where each variable resolves). The vault's scripts run through the Bash tool from skill text. Thus a script that needs the data directory must get the path from the skill text as an argument or an exported variable on the command line. It cannot read `$CLAUDE_PLUGIN_DATA` by itself. (The vault's skills already resolve the install folder this way; see `plugin/skills/design-project/SKILL.md:83` and design-critique SKILL.md:36.)
6. **`dependencies` in `plugin.json` is about other plugins, not packages.** "Plugins that must be enabled for this one to work. Each entry is `"name"`, `"name@marketplace"`, or `{ "name", "marketplace", "version" }`" (manifest reference §dependencies; `plugins/dependencies.md`). It cannot declare an npm or PyPI package.
7. **`bin/` at the plugin root goes on the Bash tool's `PATH`** while the plugin is enabled. But "claude.ai and Cowork don't install a plugin that has this directory" (manifest reference §Standard layout). The vault does not need this.
8. **MCP servers.** A plugin can declare a stdio MCP server whose `command` is `npx`/`node`, or an `.mcpb` bundle that Claude Code extracts into `.mcpb-cache/` under the plugin root (manifest reference §mcpServers). This is the route for a long-running tool server. A checker that a script calls once per page does not need it.
9. **No Python mechanism.** The docs name no automatic `pip`/`uv` install. Python dependencies go through a hook into `${CLAUDE_PLUGIN_DATA}` (loading.md:270), or the user installs them.

## 4. How other published plugins solve it

Read from the local clones under `~/.claude/plugins/marketplaces/` (anthropics/claude-plugins-official at 8f814f4, 15 Oct 2026; trailofbits at d3323ce, 2 Sep 2026) and the cached impeccable 4.5.0 and last30days 3.23.0.

1. **Most plugins avoid third-party packages.** last30days 3.23.0 has `dependencies = []` in `pyproject.toml`. trailofbits `supply-chain-risk-auditor/.../scripts/pyproject.toml` says: "Stdlib only, like every other plugin's scripts/ in this repo." The official marketplace clone holds no `package-lock.json`, `pyproject.toml`, `uv.lock` or `requirements.txt` in any of its 40 `plugins/`.
2. **`npx` / `uvx` with no pin, for MCP servers.** official `external_plugins/playwright/.mcp.json`: `npx @playwright/mcp@latest`. `external_plugins/firebase`: `npx -y firebase-tools@latest mcp`. `external_plugins/serena` and trailofbits `zeroize-audit`: `uvx --from git+https://github.com/oraios/serena`. These take the newest release on each cold start. Anthropic's own `mcp-server-dev` skill says of this route: "Local stdio (npx / uvx) — *not recommended for distribution* ... Fine for **personal tools and prototypes**. Painful to distribute: users need the right runtime" (`plugins/mcp-server-dev/skills/build-mcp-server/SKILL.md:101-105`). It recommends an MCPB bundle "packaged with its runtime" instead.
3. **Lockfile in the plugin root, install at start.** official `external_plugins/telegram` ships `package.json` (ranges `^1.0.0`, `^1.21.0`) plus `bun.lock` and `.npmrc`. Its MCP `start` script runs `bun install --no-summary && bun server.ts` in `${CLAUDE_PLUGIN_ROOT}`. The lockfile pins the versions. Claude Code's automatic install (§3.2) also reads `bun.lock`.
4. **SessionStart hook builds a Python environment outside the plugin root.** official `plugins/security-guidance/hooks/ensure_agent_sdk.py` (SessionStart, `timeout: 180`): when `claude_agent_sdk` does not import, it makes a venv at `~/.claude/security/agent-sdk-venv` and runs `pip install claude-agent-sdk` (no version pin, lines 436 and 596), with a `pip install --target` fallback. The docstring gives the reason for a folder outside the plugin root: "so it persists across plugin updates — rebuilding on every update is 30-60s of wasted work". The script handles many failure modes (no ensurepip, memory kills, a sentinel for parallel sessions).
5. **`uv run` with uv on the user's PATH.** trailofbits skills call `uv run {baseDir}/scripts/collect.py` and `uv run --no-project <plugin_root>/scripts/...` (`supply-chain-risk-auditor/SKILL.md:45`, `c-review/SKILL.md:159`). Their scripts are mostly stdlib only; `testing-handbook-skills` has `pyyaml>=6.0` and a `uv.lock`.
6. **Prompt the user to install, unvendored for licence reasons.** official `plugins/cwc-makers/skills/m5-onboard/SKILL.md:147`: "`esptool` is GPLv2+ and is intentionally **not** vendored ... The skill's preflight checks for an importable `esptool` and, if missing, prompts to install it (`python -m pip install --user esptool`)". This is the vault's current route (§1), plus an interactive prompt.
7. **impeccable 4.5.0 uses three routes at once** (`skills/impeccable/scripts/`):
   - **Vendored single-file builds**: `modern-screenshot.umd.js` (29 KB, a UMD library build) and `live-browser.js` (548 KB, a bundle) sit in the plugin and are injected into the user's page.
   - **Pinned download on first use**: the `impeccable` launcher (a POSIX shell script) looks for the engine binary next to itself, then in `~/.impeccable/bin/<VERSION>/`. When it is absent, it downloads `engine-v<VERSION>/impeccable-<os>-<arch>` from GitHub releases, checks it against a `.sha256` sidecar, and refuses to run on a mismatch or a missing sidecar ("Fail closed"). `VERSION` is `0.1.11`. The sidecar comes from the same release as the binary, so the check catches a damaged download, not a hostile release.
   - The cache is under the user's home, outside `${CLAUDE_PLUGIN_ROOT}`, so it survives plugin updates. Offline, with no cache, it fails with a setup message and exit 127.
8. **The Python axe wrapper vendors the file too.** PyPI `axe-playwright-python` 0.1.8 (24 Jul 2026, 162,584 downloads last week by pypistats) ships `axe_playwright_python/axe.min.js` (572,600 bytes, axe v4.12.1) inside its wheel and runs it with `page.evaluate(self.axe_script)` (`sync_playwright.py:32`). Deque's own `@axe-core/playwright` 4.13.0 (npm, MPL-2.0) depends on `axe-core ~4.13.0` and `playwright-core` (Node only). So "inject `axe.min.js` through Playwright" is the standard way to run axe, not a workaround.

## 5. Facts about axe-core (npm registry, GitHub and jsDelivr, read 15 Oct 2026)

1. **Version and age.** Latest is 4.14.0, released 5 Oct 2026 (10 days old today). 4.13.0 was released 5 Aug 2026; 4.12.1 on 10 Jun 2026 (`registry.npmjs.org/axe-core` `.time`; `gh api repos/dequelabs/axe-core/releases`). Canary builds come out each few days.
2. **Maintenance and use.** The package was created 8 Jun 2015. It had 337,822,950 downloads last month and 79,734,817 last week (`api.npmjs.org/downloads`). The GitHub repo is not archived, last push 14 Oct 2026, 7,652 stars. It clears `guard-npm-install.sh`'s thresholds (180 days old, 1,000 downloads a month) by far.
3. **No runtime dependencies and no install scripts.** `dependencies` is null. The `scripts` block has no `preinstall`, `install` or `postinstall` (only build, test and release scripts). The npm `dist` has `attestations` (npm provenance). Unpacked size 3,430,531 bytes in 31 files.
4. **The single file.** The package `files` list includes `axe.js` (1,477,661 bytes) and `axe.min.js` (652,140 bytes; 182,586 bytes gzipped, measured). The file is a self-contained IIFE that sets `window.axe`.
5. **Deque publishes a hash for each version.** The package ships `sri-history.json`. Its `4.14.0` entry gives `axe.min.js` as `sha256-IMCf4Veoo0ow4kGqofza3mV3NPCKs3ns++t9RcxG6Hg=`. The file downloaded from `cdn.jsdelivr.net/npm/axe-core@4.14.0/axe.min.js` hashes to the same value (measured with `openssl dgst -sha256`). Each later release repeats the earlier hashes, so a vendored file can be checked against a hash list that is not the file's own download.
6. **Licence: MPL-2.0, file-level copyleft.** The file header says: "This entire copyright notice must appear in every copy of this file you distribute or in any file that contains substantial portions of this source code." MPL-2.0 (mozilla.org/MPL/2.0) requires:
   - §3.2(a): who distributes the Executable Form must make the Source Code Form available and "inform recipients ... how they can obtain a copy". A line that names `github.com/dequelabs/axe-core` at the vendored tag does this.
   - §3.4: do not remove or alter the licence notices. Thus keep the file byte-for-byte; do not re-minify it.
   - §3.3: "You may create and distribute a Larger Work under terms of Your choice". The vault's own scripts keep their licence. Only the axe file stays MPL-2.0.
   - The design-vault repo is PRIVATE (`gh repo view`: `"visibility":"PRIVATE"`), so today the plugin goes only to the founder's own machines. The obligations stay the same if it is made public, and they cost one NOTICE line.
7. **How the vault would run it.** Python Playwright has `Page.add_script_tag(path=...)`, `Page.add_init_script(path=...)` and `page.evaluate(...)` (signatures read from the installed playwright 1.61.0). The vault scripts already inject their own JS this way: `check-access.py:794` and `:900`, `check-flow.py:1171`, `check-load.py:133`, `parts-map.py:285` call `add_init_script`. Thus axe adds no new seam: read the file, `page.evaluate(source)`, then `page.evaluate("axe.run(...)")`, which is what `axe-playwright-python` does (§4.8). **Not verified**: whether a page with a strict Content-Security-Policy blocks the injected file. `browser.new_context(bypass_csp=True)` exists in 1.61.0 as the documented switch.
8. **The CLI is the wrong unit.** `@axe-core/cli` 4.13.0 depends on `selenium-webdriver`, `@axe-core/webdriverjs` and `chromedriver: "latest"` (an unpinned range, and a package that downloads a ChromeDriver binary). It drives its own browser, not the vault's Playwright page. pa11y 10.0.0 is LGPL-3.0-only and pulls `puppeteer ^25.9.0` (a second Chromium). Lighthouse 13.5.0 has 28 dependencies and 19.2 MB unpacked.

## 6. The routes, priced

Common facts: the vault already needs Node (`check-curves.js`, `gate.js`) and Python with Playwright and Chromium on the user's machine. The repo `.gitignore` line 9 ignores `node_modules/` anywhere, so a vendored file must not sit under a folder of that name.

### (a) Vendor `axe.min.js` into `plugin/` and inject it through Playwright

- **Install time:** none for the user. The file comes with each plugin version (git-subdir copy). Each cached version grows from 864 KB (measured, `du` of `c4309eafe67f-5e689e2b`) to about 1.5 MB. Each axe bump adds about 180 KB (gzipped) to git history.
- **Offline:** works fully.
- **Pinning:** exact bytes. Record the version, source URL and sha256 next to the file. A test can compare the file hash with the value from Deque's `sri-history.json`.
- **Supply chain:** exposure only at the time of a bump, by the person who vendors it. No install scripts run, ever. The minified file is not reviewable by eye; trust comes from the npm provenance attestation and the SRI match.
- **AGENTS.md fit:** partial by its letter. The rule asks for a registry check (axe-core passes, §5.2) and "Always commit the lockfile". A vendored file has no lockfile. The version plus hash record does the same job. `guard-npm-install.sh` does not see a `curl` fetch, so the check is a written step, not an enforced one.
- **Limit:** works only for a checker that runs inside the page. Bumps are by hand; Dependabot does not see the file.
- **Precedent:** impeccable vendors `modern-screenshot.umd.js` and `live-browser.js` (§4.7); `axe-playwright-python` vendors `axe.min.js` (§4.8).

### (b) `npx` / `uvx` at run time

- **Install time:** a download on each cold cache, then the npm cache (`npm exec` docs: "installed to a folder in the npm cache"). Unknown size for a CLI; `@axe-core/cli` would also download ChromeDriver.
- **Offline:** fails on a cold cache. `--offline` works only for what is cached.
- **Pinning:** the top package only (`pkg@x.y.z`). A published npm package carries no `package-lock.json` (Claude Code loading.md:244: "npm excludes `package-lock.json` from published packages"), so the dependencies under it resolve from ranges at fetch time. `uvx pkg@ver` pins the top package; the uv tools guide does not say that its dependencies are locked.
- **Supply chain:** the highest of the five. Fresh resolution on each cold cache. In npm 11.16.0 (this machine), `allow-scripts` is empty and `strict-allow-scripts` is false, so a dependency's install scripts still run "with a notice" (npm `config.md:253-265`, `:1831-1843`).
- **AGENTS.md fit:** fails. There is no lockfile to commit, and `guard-npm-install.sh` check 3 denies a bare `npx` of an unscoped package that `package.json` does not list. `uv` is not installed on this machine (`which uv uvx` finds nothing).
- **Precedent:** official Playwright, Firebase and Serena plugins use it, with `@latest` or a git URL.

### (c1) Pinned install by Claude Code itself: `plugin/package.json` plus `plugin/package-lock.json`

- **Mechanism:** Claude Code's automatic Node dependency install (§3.2). Add `plugin/package.json` with `"dependencies": { "axe-core": "<exact>" }` and an npm lockfile (v3). Claude Code then runs a frozen, script-free, registry-only install into `${CLAUDE_PLUGIN_ROOT}/node_modules` at install, update and first session on a new machine. The Python script reads `<plugin root>/node_modules/axe-core/axe.min.js`.
- **Install time:** one `npm` install per plugin version, with a 60-second limit. Not measured. axe-core is one package with no dependencies, so the estimate is a few seconds, and less when the npm cache has it. The vault released about 82 versions in 16 days (82 cache folders, 78 marked orphaned), so the install runs at each release.
- **Offline:** works after a good install. When the install fails or `npm` is absent, "the plugin still loads, but the parts of it that need the missing packages may not work" (loading.md:266). The script must then report the missing file and name `claude plugin update design-vault@lucmoseley`.
- **Pinning:** exact, by the lockfile and its sha512 `integrity`.
- **Supply chain:** low. Claude Code forces `--ignore-scripts`, frozen resolution and `https`, and ignores the plugin's `.npmrc` (loading.md:248-262). Exposure is at each install on each machine, against the pinned integrity hash.
- **AGENTS.md fit:** full. A registry check and a committed lockfile are exactly what it asks for. A session that writes the lockfile runs `npm install --ignore-scripts --save-exact` in `plugin/` and meets the guard.
- **Open points (not verified, test before use):** (1) whether `devDependencies` are installed. (2) That a `git-subdir` plugin gets the install. The docs say "Every other marketplace plugin" is copied and gets it, which includes git-subdir, but no vault release has tried it. (3) The repo needs a second manifest in `plugin/` beside the root `package.json` (shfmt), and `test/all.sh` needs `npm ci --ignore-scripts --prefix plugin` (or a path fallback) so the repo suites find the file. (4) Each version folder holds its own 3.4 MB copy until the 14-day cleanup.

### (c2) Pinned install from a SessionStart hook into `${CLAUDE_PLUGIN_DATA}`

- **Mechanism:** the docs' hook (§3.4), with a copied lockfile and `npm ci --ignore-scripts` in place of the docs' bare `npm install`. One install survives all plugin updates.
- **Install time:** each session start runs a `diff` (milliseconds). The first session and each change of the manifest run the install inside the hook's timeout.
- **Offline:** works after the first good install.
- **Pinning and supply chain:** as good as (c1) only if the hook copies the lockfile and passes `--ignore-scripts`. The docs' example does neither. The hook runs as the user on each machine, outside `guard-npm-install.sh` (that guard reads only the Bash tool).
- **AGENTS.md fit:** full if the lockfile is committed.
- **Extra cost:** the Bash tool does not receive `CLAUDE_PLUGIN_DATA` (§3.5). Each skill line that runs the script must pass `${CLAUDE_PLUGIN_DATA}` from the skill text.
- **Use:** this is the only documented route for **Python** packages in a plugin. It is a candidate later for pinned numpy, Pillow and scipy in a venv under the data directory. It does not cover Chromium well: Playwright keeps browsers per machine, and a Chromium download is large for a hook timeout.

### (d) Bundle into one committed file (esbuild or ncc)

- **For axe:** not needed. `axe.min.js` already is the bundle. This route reduces to (a).
- **For a Node-side checker with dependencies** (stylelint 17.16.0 has 35, htmlhint 1.9.2 has 8): build one file in the repo with esbuild (0.28.2, MIT) or `@vercel/ncc` (0.45.0, MIT) and commit it under `plugin/`. The build tools stay devDependencies in the repo root lockfile.
- **Install time / offline / pinning:** as (a): none, works offline, exact bytes, with the repo lockfile recording what went in.
- **Supply chain:** exposure at build time only, but a bundle mixes many packages into one file that nobody reviews. esbuild keeps `/*!`, `@license` and `@preserve` comments, moved to the end of the file by default when it bundles ("The default behavior is `eof` when bundling is enabled", esbuild API §Legal comments).
- **Limits:** a tool that loads plugins or configs by a dynamic `require` (stylelint does) or needs a native module may not bundle. A rebuild check is needed so the committed file matches the lockfile.
